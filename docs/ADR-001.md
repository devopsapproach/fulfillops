# ADR-001 — Adopt an API-and-worker architecture with PostgreSQL-backed jobs

Status — Proposed
Owners — Jaimie, Iulian, Sultan

## Context

FulfillOps must accept orders quickly, reserve stock safely, and complete
orders asynchronously.

Clients may repeat requests, multiple API instances may accept orders
concurrently, and workers may restart during processing.

Accepted orders and their pending work must survive process restarts.

The three-person team has a total project budget of 45–55 shared hours.

## Decision

Use an Express HTTP API and a separate background worker in one
TypeScript repository.

Use PostgreSQL as the shared durable store for inventory, orders,
order items, processing jobs, and fulfillment receipts.

Commit order creation, inventory reservation, and job creation in one
database transaction.

Workers consume jobs directly from the PostgreSQL work table.

The final deployment supports two API replicas and two worker instances.

## Alternatives considered

### PostgreSQL with Redis Streams

A dedicated broker could separate queue delivery from database operations.

It would also introduce another persistent service and require reliable
coordination between the PostgreSQL transaction and message publication,
such as a transactional outbox and relay.

For the current scope, the team chooses a PostgreSQL work table.

### Synchronous processing inside the API

Completing work during the HTTP request would couple acceptance latency
to processing time and would not satisfy the separate-worker requirement.

### In-memory job storage

Pending work would be lost when the process restarts, violating the
durability requirement.

## Consequences

Order acceptance and job creation share one atomic commit.

The team operates one durable storage system for application data and jobs.

Queue polling and business queries share database resources.

PostgreSQL availability affects both order acceptance and processing.

The team must implement safe job claiming, bounded retries, recovery,
and guarded completion.

A unique completion receipt helps enforce one database fulfillment outcome.
Future external shipping or payment integrations would need their own
idempotency strategy.
