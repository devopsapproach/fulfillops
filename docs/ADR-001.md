# ADR-001 — Initial FulfillOps architecture

Status — Proposed
Owners — All three developers

## Scope

Deliver a local API, separate worker, and PostgreSQL database.
Demonstrate safe order acceptance and asynchronous completion.

## Stack

Node.js, TypeScript, Express, PostgreSQL, Prisma,
Zod, Vitest, Supertest, Docker Compose.

## Data model

Products, orders, order items, jobs, fulfillment receipts.

## Invariants

- Stock is never negative.
- One idempotency key identifies at most one accepted order.
- Order, reservation, and job are committed together.
- An order has at most one fulfillment receipt.
- Accepted orders and idempotency mappings survive restarts.

## Order states

queued, processing, completed, failed.

## Job states

pending, running, completed, failed.

## Transaction boundaries

Acceptance, job claiming, completion, retry scheduling,
and final failure each have an explicit transaction boundary.

## Interfaces

API writes orders and jobs.
Worker claims jobs and commits completion.
Both use the shared database configuration.

## Data model

The Prisma schema defines application-facing model and field names.
SQL table and column names use explicit mappings.

| Prisma model       | SQL table            | Main guarantees                                              |
| ------------------ | -------------------- | ------------------------------------------------------------ |
| Product            | products             | Unique SKU, nonnegative stock and price                      |
| Order              | orders               | Unique idempotency key, nonnegative total                    |
| OrderItem          | order_items          | Unique order/SKU pair, positive quantity                     |
| Job                | jobs                 | One job per order, bounded attempts, consistent claim fields |
| FulfillmentReceipt | fulfillment_receipts | One completion receipt per order                             |

Money is stored as integer cents.
Timestamps use PostgreSQL TIMESTAMPTZ.
Foreign keys use restricted deletion and updates.

Order items capture the unit price at acceptance.
Repeated SKU lines are aggregated before their item records are created.

## Database constraints and indexes

Custom migration SQL enforces:

- Nonnegative inventory and monetary values.
- Positive item quantities.
- Positive maximum attempts and bounded attempt counts.
- Claim token and lease presence exactly while a job is claimed.
- Terminal timestamps consistent with order and job states.

Partial indexes support pending-job scheduling and expired-lease lookup.

Database constraints protect individual records.
Cross-table state consistency is enforced by application transactions.

## Order states

The public order states are:

- queued
- processing
- completed
- failed

## Job states

The internal job states are:

- pending
- claimed
- completed
- dead_letter

| Event                                  | Job transition         | Order transition        |
| -------------------------------------- | ---------------------- | ----------------------- |
| Acceptance                             | New to pending         | New to queued           |
| Claim                                  | pending to claimed     | queued to processing    |
| Success                                | claimed to completed   | processing to completed |
| Retry scheduled                        | claimed to pending     | processing to queued    |
| Lease recovery with attempts remaining | claimed to pending     | processing to queued    |
| Attempts exhausted                     | claimed to dead_letter | processing to failed    |

These transitions define the intended worker behavior.
The worker startup skeleton does not yet implement all transitions.

## Transaction boundaries

Order acceptance commits the order, item records, inventory reservation,
and job together.

Workers claim eligible jobs in short transactions.
Each claim increments attempts and establishes a fresh token and lease.

Completion verifies current ownership, inserts the unique receipt, and
updates the job and order together.

Retry and final-failure updates also verify ownership and update the order
and job together.

Expired claims are recovered only after their state and lease are
rechecked under a lock.

Failed orders retain their reserved stock for operator reconciliation.

## Idempotency and concurrency

An idempotency key identifies at most one accepted order.

The API compares canonical request payloads when handling a repeated key.
Canonicalization preserves the customer identifier, aggregates duplicate
SKU lines, and sorts items by SKU.

Matching replays return the original order ID and queued acceptance receipt.
Different payloads using the same key produce an idempotency conflict.

Product rows are locked in deterministic SKU order to reduce deadlock risk.
Transient transaction retries must be bounded.

## Timestamp ownership

created_at is initialized when a record is inserted.

Application updates explicitly refresh updated_at, including raw SQL writes.

Claiming establishes lease_expires_at.
Leaving the claimed state clears claim_token and lease_expires_at.

Terminal timestamps are set in the corresponding completion or failure
transaction.

## Shared database interface

shared/database.ts exports one Prisma client per application process,
named database.

Both API and worker code use this shared configuration.
Each process disconnects its client during shutdown.

The seed script uses the same client and closes it when execution ends.

## Configuration

DATABASE_URL selects the application or migration database.

TEST_DATABASE_URL selects the isolated integration-test database.

POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB, and POSTGRES_PORT configure
the local Compose database.

Worker lease, polling, and retry settings are environment-configurable.
Each job stores its own maximum attempt budget.

Real credentials stay outside Git.

## Migrations and seeding

Prisma models and SQL migrations are committed to Git.

Custom SQL constraints and partial indexes are added to draft migrations
before their first application.

Applied and shared migrations are preserved.
Subsequent changes receive new migrations.

Seeding inserts missing catalog products and preserves existing stock
and prices. Test-data reset is a separate guarded operation.
